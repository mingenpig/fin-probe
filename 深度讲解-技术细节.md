## 第一部分：架构的三个层次

### 1. 为什么不能用 Single-Agent 来处理三个领域

#### 问题场景
用户问："请全面排查供应商 VEN-0044"

这个问题涉及三种完全不同的**业务逻辑和数据模型**：

| 领域 | 调查重点 | 必查工具 | 分级规则 | 关键单据 |
|------|--------|--------|--------|--------|
| **供应商** | 法律风险、重复建档 | vendor-query approval-query | 档案缺失 > 改档频繁 > 关联 | VEN-0044 本身 |
| **交易** | 数量匹配、税率合规 | po-query gr-query invoice-query | 数量差% > 金额差 > 税率 | PO + GR + INV |
| **支付** | 重复付款、账户安全 | payment-query vendor-query | 重复次数 > 账户类型 | PAY + 账户信息 |

#### 为什么 Single-Agent 会出错

**1. 关键词冲突导致误路由**

```
用户: "差旅住宿标准"
Single-Agent 错误思路：
  → 看到"住宿"和"标准"
  → 想起"供应商管理办法有住宿条款"
  → 派给 SupplierRiskAgent
  → 错了！应该是制度问答，返回政策，不要判风险

Multi-Agent 路由：
  → LeadAgent 看到"差旅"不看到"供应商"或"单据号"
  → 判定 mode = policy_qa
  → 派给 GeneralQueryAgent
  → 对了！
```

**2. 分级标准的混乱**

```
同样是"两笔付款"：

TransactionRiskAgent 视角：
  → 两张发票各付一次 = 正常（不是「重复」）
  
PaymentRiskAgent 视角：
  → 同一张发票付了两次 = 高风险（没有中风险档）
  
SupplierRiskAgent 视角：
  → 两个子公司各付一次 = 可能是关联交易风险

Single-Agent 看到"两笔"，会搞混这三种语义。
```

**3. 上下文的信息超载**

```
Single-Agent 需要加载：
  ✓ supplier-profile-audit-skill (档案、税号、电话冲突)
  ✓ supplier-relation-audit-skill (关联交易、同控人)
  ✓ p2p-three-way-match-skill (数量、单价、税率、发票号)
  ✓ split-order-audit-skill (拆单、5日聚类、红线判断)
  ✓ payment-audit-skill (PAID 次数、invoice 关联)
  ✓ payee-account-security-skill (账户类型、银行、个人卡)
  ✓ internal-policy-qa-skill (制度、限额、审批门槛)
  ✓ general-query-skill (查单、澄清)
  ✓ evidence-validation-skill (证据审核)
  ✓ risk-report-generator-skill (报告生成)

总共 10 个 Skill，每个 1-2K tokens。就算只用其中 3 个，加载时的冗余信息也会影响推理质量。

Multi-Agent：
  → SupplierRiskAgent 只看 2 个 Skill
  → TransactionRiskAgent 只看 2 个 Skill
  → PaymentRiskAgent 只看 2 个 Skill
  → 每个 Agent 上下文清爽，决策也准确
```

#### 核心结论

```
Single-Agent = 全能医生 → 样样懂，样样不精
Multi-Agent = 专科医院 → 各科专家 + 总协调 + 质控部门
```

```python
def decide_route(question: str) -> RouteObject:
    """
    这个函数是整个系统的"分诊台"
    """
    
    # 第 0 步：提取实体
    subject = extract_subject(question)
    # 返回: {supplierId, poId, grId, invoiceId, paymentId, supplierName, taxNo}
    
    # 正则匹配例子：
    # "VEN-0044" → supplierId
    # "PO-01332" → poId
    # "公司名称有限公司" → supplierName
    # "91330100MA..." → taxNo
    
    # 第 1 步：判断是否有可绑定的实体
    has_entity = subject.supplierId or subject.poId or ...
    
    # 第 2 步：检查意图关键词
    is_policy = "制度" in question and "风险" not in question
    is_cross = "全面排查" in question or "从采购到付款" in question
    is_lookup = "查一下" in question and "风险" not in question
    
    # 第 3 步：优先级决策（从上到下）
    
    if is_policy and not is_cross:
        # 优先级最高：纯制度问题，不会进其他路由
        return RouteObject(
            mode="policy_qa",
            agents=["GeneralQueryAgent"],
            skills=["internal-policy-qa-skill"],
            wantReport=False
        )
    
    if not has_entity and not is_policy:
        # 次优先级：缺实体，问澄清
        return RouteObject(
            mode="clarify",
            clarifyQuestion="请提供供应商名称/ID 或 PO/发票单号",
            wantReport=False
        )
    
    if is_lookup and not is_cross:
        # 查单但不要结论
        return RouteObject(
            mode="lookup",
            agents=["GeneralQueryAgent"],
            skills=["general-query-skill"],
            wantReport=False
        )
    
    # 以下才考虑风险调查
    
    if is_cross or (有供应商 and "全面" in question and 无单据号):
        # 跨域或全面排查
        return RouteObject(
            mode="cross",
            agents=[SupplierRiskAgent, TransactionRiskAgent, PaymentRiskAgent],
            skills=[全部6个Skill],
            wantReport=True
        )
    
    # ... 更多规则处理单一领域情况
```

### 3. 并行 vs 串行 的精确控制

#### 支付 Agent 的等待条件

```python
def payment_must_wait(subject: Subject) -> bool:
    """
    这是关键的任务依赖判断
    """
    # 如果已经有 invoiceId 或 paymentId，不用等
    return not bool(subject.invoiceId or subject.paymentId)

# 使用场景：

# 场景 A：用户给了 invoiceId
# 用户: "发票 INV-003948 有没有重复付款风险"
# subject: {invoiceId: "INV-003948"}
# payment_must_wait() → False
# → Payment Agent 可以立刻并行运行

### 2. 沙箱执行的规则

#### financial-analysis 工具的限制

```python
def execute_financial_analysis(artifactIds: list, code: str) -> dict:
    """
    沙箱只允许特定的操作
    """
    
    # ✅ 允许的操作
    allowed = {
        "defaultdict": defaultdict,
        "Counter": Counter,
        "to_number": to_number,  # 自定义：字符串转数字
        "math": math,
        "datetime": datetime,
        "isinstance": isinstance,
        "try/except": True,
    }
    
    # ❌ 禁止的操作
    forbidden = {
        "import": "不能导入新库",
        "type()": "不能调用 type()",
        "getattr/setattr": "不能访问对象属性",
        "__dict__": "不能访问私有属性",
    }
    
    # 验证代码
    if "import " in code:
        return {"error": "禁止 import"}
    
    if "type(" in code:
        return {"error": "禁止 type()"}
    
    if "result = " not in code:
        return {"error": "必须赋值 result = {...}"}
    
    # 加载 artifact
    artifacts = {}
    for artifact_id in artifactIds:
        artifacts[artifact_id] = load_artifact(artifact_id)
    
    # 执行
    namespace = {
        **allowed,
        "invoices": artifacts.get(artifactIds[0], [])
    }
    
    try:
        exec(code, namespace)
        result = namespace.get("result")
        return {"ok": True, "result": result}
    except Exception as e:
        return {"error": str(e)}
```

class RuleChecker:
    def check(self, envelope: Envelope) -> list[RuleFinding]:
        findings = []
        
        # 检查 1：必查工具的齐全性
        required_tools = REQUIRED_TOOLS_FOR[envelope.findings[0].riskType]
        called_tools = {q.tool for q in envelope.queries}
        
        if not required_tools.issubset(called_tools):
            findings.append({
                "severity": "blocker",
                "message": f"缺少工具 {required_tools - called_tools}",
                "relatedIds": envelope.subject.model_dump().values()
            })
        
        # 检查 2：单据 ID 的追踪
        for finding in envelope.findings:
            for fact in finding.facts:
                # 从 fact 提取 ID（"PO-01332 订 100 件"）
                ids = re.findall(r"(PO|GR|INV|PAY)-\d+", fact)
                for id in ids:
                    # 检查这个 ID 是否在 evidenceRefs 中
                    if id not in [ref.id for ref in finding.evidenceRefs]:
                        findings.append({
                            "severity": "major",
                            "message": f"结论引用 {id} 但未在 evidenceRefs 中"
                        })
        
        # 检查 3：大结果处理
        for query in envelope.queries:
            if query.totalCount > 8 and not query.artifact:
                findings.append({
                    "severity": "blocker",
                    "message": f"{query.tool} 返回 {query.totalCount} 条但缺 artifact"
                })
        
        return findings

### 2. 语义层检查（需要模型）

```python
class SemanticChecker:
    def check(self, envelope: Envelope) -> list[SemanticFinding]:
        findings = []
        
        # 检查 1：风险等级与阈值是否一致
        for finding in envelope.findings:
            if finding.riskType == "少货多付 / 数量/金额异常":
                qty_diff = finding.metrics.get("quantityDiffPercent", 0)
                
                if qty_diff > 10 and finding.riskLevel != "高风险":
                    findings.append({
                        "severity": "major",
                        "message": f"数量差 {qty_diff}% > 10% 应为高风险，"
                                 f"但判定为 {finding.riskLevel}"
                    })
                
                elif 2 < qty_diff <= 10 and finding.riskLevel not in ["中风险", "低风险"]:
                    findings.append({
                        "severity": "major",
                        "message": f"数量差 {qty_diff}% 应为中风险，"
                                 f"但判定为 {finding.riskLevel}"
                    })
        
        # 检查 2：消解的真实性
        for finding in envelope.findings:
            if "已消解" in finding.recommendation or \
               "已批准" in finding.recommendation:
                
                # 检查是否真的有 approval-query
                approval_queries = [q for q in envelope.queries 
                                   if q.tool == "approval-query"]
                
                if not approval_queries:
                    findings.append({
                        "severity": "major",
                        "message": "声称已消解/批准，但 queries 中没有 approval-query"
                    })
                
                elif approval_queries[0].totalCount == 0:
                    # 允许 NOT_FOUND，但不能说"已批准"
                    if "已批准" in finding.recommendation:
                        findings.append({
                            "severity": "major",
                            "message": "approval-query 返回 0 条，不能说'已批准'"
                        })
        
        # 检查 3：根因的质量
        for finding in envelope.findings:
            if finding.riskLevel in ["高风险", "中风险"]:
                
                if finding.rootCause in ["对不上", "异常", "不一致", "问题"]:
                    findings.append({
                        "severity": "major",
                        "message": "根因只复述现象，需要说明业务机制"
                                 f"（而不是'{finding.rootCause}'）",
                        "example": "短收仍按订单全额开票"
                    })
        
        return findings
```

### 3. 补查循环的实现

```python
async def evidence_review_loop(
    evidence_bag: EvidenceBag,
    max_rounds: int = 2
) -> ReviewResult:
    """
    补查最多 2 轮，共 3 次审核
    """
    
    for round_num in range(max_rounds):
        # 第 N 轮审核
        review = await evidence_review_agent.run(evidence_bag)
        
        if review.readyForReport:
            # 证据充分，可以出报告
            return review
        
        if not review.followUpTasks:
            # 有问题但不需要补查（比如纯语义错误）
            return review
        
        # 需要补查
        print(f"发现缺口，第 {round_num + 1} 轮补查...")
        
        for task in review.followUpTasks:
            # 调对应的 Agent 补查
            agent = agents_by_skill[task.skill]
            new_envelope = await agent.run(
                skill=task.skill,
                args=task.args,
                subject=evidence_bag.subject
            )
            
            # 更新证据袋
            evidence_bag.envelopes.append(new_envelope)
        
        # 继续下一轮审核
    
    # 补查 2 轮后仍有问题
    return review  # readyForReport = False
```

### 2. 评测指标的定义

```python
class RoutingMetrics:
    """评测路由准确率"""
    
    def __init__(self, gold_cases: list):
        self.gold = gold_cases
        self.results = []
    
    def evaluate(self):
        for case in self.gold:
            route = decide_route(case["question"])
            expected = case["expected"]
            
            # 精确匹配
            exact_match = (
                route.mode == expected["mode"] and
                set(route.agents) == set(expected.get("agents", [])) and
                set(route.skills) == set(expected.get("skills", []))
            )
            
            # 部分匹配（mode 和 agents 子集）
            partial_match = (
                route.mode == expected["mode"] and
                set(route.agents).issubset(set(expected.get("agents", [])))
            )
            
            self.results.append({
                "question": case["question"],
                "exact": exact_match,
                "partial": partial_match,
                "route": route,
                "expected": expected
            })
    
    def report(self):
        exact_acc = sum(1 for r in self.results if r["exact"]) / len(self.results)
        partial_acc = sum(1 for r in self.results if r["partial"]) / len(self.results)
        
        print(f"精确匹配: {exact_acc * 100:.1f}%")
        print(f"部分覆盖: {partial_acc * 100:.1f}%")
        
        # 错误分析
        errors = [r for r in self.results if not r["exact"]]
        for error in errors[:5]:  # 展示前 5 个错误
            print(f"\n❌ {error['question']}")
            print(f"  期望: {error['expected']}")
            print(f"  实际: {error['route'].to_dict()}")
        
        return {
            "exact": exact_acc,
            "partial": partial_acc,
            "error_count": len(errors)
        }
```

## 第五部分：常见面试追问与深度回答

### Q1: "为什么 EvidenceReviewAgent 不直接改结论，而是产生 followUpTasks？"

**背景**：这考察你对**权限分离和审计制衡**的理解。

**深度回答**：

```
这涉及两个层面的设计原则：

【技术层面】
- 如果 EvidenceReviewAgent 自己改结论，就没有人知道原来的 Agent 想说什么
- 这违反了"可审计性"原则
- 比如：财务部门想查"为什么这个风险等级从高风险改成了低风险"，无法追溯

【业务层面】
- 不同 Agent 有不同的信息和权限
- EvidenceReviewAgent 只看"这个结论有没有被证据支撑"
- 但结论怎么改，该由原来的 Agent（更了解这个领域的 Agent）来决定
- 比如：
  ✗ EvidenceReviewAgent 不应该说"这个税率异常从高风险改成中风险"
  ✓ EvidenceReviewAgent 应该说"缺少 approval-query，建议 TransactionRiskAgent 补查"

【制度设计】
这其实是在模拟企业审计的流程：
  审计部门 → 发现问题 → 提出改进建议 → 业务部门 → 补齐证据 → 审计部门 → 确认

而不是：
  审计部门 → 直接改掉业务部门的结论 (这样会引起纠纷)
```

### Q2: "如果补查了 2 轮还有 blocker，系统怎么给用户交代？"

**背景**：这考察你对**不完美情况下系统设计**的理解。

**深度回答**：

```
有两个选择，取决于 blocker 的性质：

【选择 1】输出"证据不足"
- 场景：缺必要的审批记录，真的无法查到
- 表述给用户："ERP 未检索到该订单的补货审批。建议人工核实供应商是否真的有补货。"
- 优点：诚实，不造假
- 缺点：用户可能不满意（但这比假结论要好）

【选择 2】输出"草稿 + 缺口清单"
- ReportAgent 输出一份报告，但标注：
  "⚠️ 以下缺口需要人工补充：
   - PO-01332 的税率变更审批（影响税率异常判定）
   - VEN-0044 的最新工商变更记录（影响档案异常判定）"
- 优点：给用户可用的中间结果，又诚实标注了缺陷
- 缺点：需要定义哪些缺口是"可容忍的"，哪些是"致命的"

【从产品角度】
我个人倾向选择 2，因为：
- 用户可以拿到 80% 完成的调查
- 知道剩下 20% 需要什么
- 而不是被完全挡在外面

这就是所谓的"优雅降级"。
```

### Q3: "Multi-Agent 并行运行会不会有竞态条件？"

**背景**：这考察你对**并发系统**的理解。

**深度回答**：

```
【可能的竞态条件】

1. 证据袋的写冲突
   场景：三个 Agent 同时更新 evidence_bag
   
   SupplierRiskAgent: evidence_bag.envelopes.append(s_envelope)  ← 并发写
   TransactionRiskAgent: evidence_bag.envelopes.append(t_envelope)  ← 并发写
   PaymentRiskAgent: evidence_bag.envelopes.append(p_envelope)  ← 并发写

【解决方案】

1. 串行化证据袋的写入
   ```python
   # 用锁保护 evidence_bag 的修改
   async def orchestrate():
       s_task = create_task(supplier_agent.run())
       t_task = create_task(transaction_agent.run())
       p_task = create_task(payment_agent.run())
       
       # 等三个都完成
       s_env, t_env, p_env = await gather(s_task, t_task, p_task)
       
       # 然后串行地合并（不是并发的）
       evidence_bag = EvidenceBag()
       evidence_bag.envelopes.append(s_env)
       evidence_bag.envelopes.append(t_env)
       evidence_bag.envelopes.append(p_env)
   ```

2. Subject 的版本管理
   ```python
   # 不在 Agent 之间直接修改 Subject
   # 而是返回补齐的字段，由 LeadAgent 做 merge
   
   t_result = await transaction_agent.run(subject=base_subject)
   
   # t_result 返回: {invoiceId: "INV-003948"}
   
   # LeadAgent 合并（串行）
   merged_subject = merge_subject(base_subject, t_result.subject)
   
   # Payment Agent 用合并后的 subject
   p_result = await payment_agent.run(subject=merged_subject)
   ```

【为什么这样设计没问题】

- Agent 之间不直接修改共享状态
- Agent 返回的结果是 immutable 的（信封，包含证据)
- LeadAgent（单线程）负责合并，所以没有竞态
- 这叫 "Actor 模型"的思想

【从产品角度】

不需要关心这些技术细节，但理解这一点：
- Multi-Agent 系统需要"协调者"（LeadAgent）
- 协调者防止了混乱
- 这就是为什么 LeadAgent 存在，而不是让三个 Agent 自己沟通
```

## 总结：五个关键洞察

| 洞察 | 为什么重要 | 面试时怎么说 |
|------|----------|-----------|
| **分层 ≠ 分散** | 多 Agent 需要清晰的职责边界和协调者 | "LeadAgent 是分诊台，不是中介。" |
| **证据 > 感觉** | 风险结论必须能指回具体的单据和审批 | "调查、审核、补查、报告四个环节缺一不可。" |
| **规则外化** | Skill 用 Markdown 写，不在代码里 | "这样财务合规人员也能理解系统逻辑。" |
| **大数据分层** | 不是把全量数据塞进模型 | "summary/sample/artifact 三级返回，既省 Token 又不丢信息。" |
| **优雅降级** | 系统不完美但诚实，比假装完美要好 | "补查 2 轮还有问题就输出『证据不足』，不造假。" |
